# Decisions

| # | Decision | Why |
|---|---|---|
| D1 | The Super Admin dashboard keeps its original `index.html` markup, `styles.css`, `charts.js`, `scenes.js` and `app.js`, vendored in `src/legacy/admin/` and run on the `three` npm package. Only the data source, live feed, mutations and export are wired to the backend. | Owner instruction: "as it is, no changes". Rewriting 100 KB of tuned UI into React components would change it. |
| D2 | One admin RPC, `admin_snapshot()`, returns the exact `PCV_DATA` shape the dashboard already consumes (users with per-user aggregates, 365-day daily series, cohorts, heatmap, files, audit). | Simplest contract that keeps `app.js` unchanged; range math stays client side. About 100 bytes per user. |
| D3 | The "Who saw your page" card is ported to a React component with its CSS and three.js ribbon unchanged; it opens from the prototype's eye pill. The 30 days and All time buttons are enabled with real data (the design marked them "Not in this preview"). | DESIGN.md section 13 requires the three ranges. |
| D4 | Editor, viewer, auth and picker screens are React components built from `prototype/Main.dc.html`, with its CSS copied as is. | The prototype is a template DSL that has to be translated anyway. |
| D5 | Anonymous access goes through security-definer functions (`get_public_portfolio`, `portfolio_stats`, `record_visit`, `touch_visit`, `open_document`) instead of anon RLS policies on tables. | Returns only public columns (never email); a table policy would expose whole rows. |
| D6 | Documents are opened through `/d/<id>`, which checks the owner is not disabled, records the open and redirects (presigned 5 min GET for files, the URL for links). | One place for authorization and "files opened" tracking. |
| D7 | Uploads go browser to R2 with a presigned PUT (5 min); the server then HEADs the object to confirm size and type before the document becomes visible. | Files never pass through the server; the server still validates. |
| D8 | Delete account runs in one database transaction (`admin_delete_account`) that also writes the audit row; R2 objects are deleted after commit. | Audit and delete are atomic. An R2 failure leaves orphans, which are logged. |
| D9 | "Needs a look": the "reported by viewers" row is removed (no reporting feature in the MVP); the on-hold wait time is computed; its action ("Show") filters the users table to "Other" organisations. Export downloads a CSV. Toast copy for Add user no longer promises an email. | No fake numbers or fake actions. |
| D10 | Local development and tests use the Supabase CLI stack (Docker) and an S3-compatible mock (`s3rver`) for R2. E2E tests sign in with a password created through the admin API, then hand the session cookies to the browser. The app itself only offers Google. | Google OAuth cannot run headless without real credentials. |
| D11 | The first super admins come from `admin_allowlist`; everyone else starts as an Editor. | No trusted client-side role, no hardcoded emails. |
| D12 | three.js is pinned to r128 (`three@0.128.0`), the version both dashboards were written for. | Newer three changes colour management and lighting, so the scenes would look different. |
| D13 | The site and the admin dashboard have separate root layouts; links between them are full page loads. | The dashboard's CSS uses generic class names (`.card`, `.palette`, `.swatch`) that collide with the prototype's. |
| D14 | Deviations from supplied CSS live in `src/styles/fixes.css`, each with the bug it fixes; the one exception is the declaration order of `backdrop-filter` in `whosaw.css` (values unchanged), noted in that file. | Keeps the supplied files as they are and makes every change reviewable. |
| D15 | Next.js upgraded from 16.3.5 to 16.4.3. | 16.3.5 has a critical remote code execution advisory and six others; 16.4.3 has none. |
| D16 | The table picker shows neutral placeholder rows ("Your first project") only while a page is empty, instead of the prototype's sample projects. | No prototype sample data in the product. |
| D17 | Visit and file-open counting is server only (service role) and limited per network by an HMAC of the IP. | Stops scripted inflation without storing IPs. |
| D18 | Storage quota: 100 MB per file, 1 GB per account, exact upload size (signed Content-Length, HEAD, database check). | Owner's request to close the "no storage cap" risk. |
| D19 | CSP with a per-request script nonce and 'strict-dynamic'; styles allow inline. | The design system uses style attributes; scripts are where injection runs. |
| D21 | Motion: loading screens are CSS skeletons per area (`loading.tsx`; dark and lime in the app, beige and gold on sign-in, a dashboard outline for the admin start-up). Richer interactions use GSAP (dialog spring, new-row arrival, success sparks, sign-in pointer depth), always switched off for reduced motion and touch. Main actions use one `StateButton` (idle, busy with real upload progress, done). Moving between screens inside the app uses an iris: the dome irises shut from the click, the next screen loads hidden behind it, then it opens from the centre (`PageTransition.tsx`, no skeleton is seen on these moves); full page loads use the browser's cross page view transition with the same opening where supported. The public page `/p/[slug]` has no loading screen. | Owner request; ActionScript cannot run in browsers, GSAP is its successor for timeline and spring work. A loading screen on the public page would make unknown or disabled pages answer 200 instead of 404, and flash a dark skeleton before an owner's light wallpaper. |
| D20 | Wallpapers, table styles and colours live in a `catalog` table that super admins manage from section 05. New wallpapers are uploaded images; new tables reuse a built-in design with their own colours; items are hidden, never deleted. | Owner request. Uploaded images and preset designs cannot break a page the way pasted CSS could, and hiding keeps every existing page working. Images are served via `/w/<id>` as a day-stable signed R2 link so browsers cache them. |
